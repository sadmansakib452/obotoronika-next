# Database Design Phase

## When to Run DB Design

**Full design needed when:**
- Creating 1+ new tables
- Adding complex columns (JSONB, arrays, foreign keys)
- Changing table relationships
- Adding enums or constraints

**Skip design phase when:**
- Adding a single nullable column (string, integer, boolean)
- Adding a simple index to an existing column
- Can go straight to implementation

## Design Phase Steps

### 1. Propose Schema
Before any migration, present:
- New tables with all columns + types
- Foreign key relationships
- Indexes (for WHERE, JOIN, ORDER BY columns)
- Enums for fixed-value columns
- Constraints (NOT NULL, UNIQUE, CHECK)
- Default values

### 2. Migration Rules
- ALWAYS make migrations reversible (`def up` + `def down` OR `def change` for reversible ops)
- Use `add_index` for frequently queried columns
- Set appropriate defaults for NOT NULL columns
- Use `null: false` where values are required
- Add `foreign_key: true` for references

```ruby
# ✅ Good: Reversible with indexes and defaults
class CreateReviews < ActiveRecord::Migration[8.0]
  def change
    create_table :reviews do |t|
      t.references :product, null: false, foreign_key: { to_table: :spree_products }
      t.references :user, null: false, foreign_key: { to_table: :spree_users }
      t.integer :rating, null: false, default: 5
      t.text :body
      t.boolean :approved, null: false, default: false
      t.timestamps
    end

    add_index :reviews, :rating
    add_index :reviews, [:product_id, :approved]
  end
end
```

### 3. Rollback Strategy
Before running `db:migrate`, confirm the rollback works:
```bash
# Always know the rollback command
bin/rails db:rollback STEP=1
```

For non-reversible migrations, provide explicit rollback instructions.

### 4. After Migration
- Run `bin/rails db:migrate`
- Verify in `db/schema.rb` that the version updated
- Check production migration safety: no locking on large tables, no data loss
- Update any seed data if needed

## Index Guidelines

### Always Index
- Foreign key columns
- Columns used in WHERE clauses frequently
- Columns used in ORDER BY
- Columns used in JOIN conditions
- Unique constraint columns (automatic)

### Composite Indexes
- Order matters: put most selective column first
- Cover query patterns: WHERE a AND b → index on [a, b]
- Don't over-index: each index slows writes

```ruby
# For: WHERE product_id = ? AND approved = ? ORDER BY created_at DESC
add_index :reviews, [:product_id, :approved, :created_at]
```

## N+1 Prevention
Always use `includes` or `eager_load` for associations:
```ruby
# ❌ N+1
products = Spree::Product.all
products.each { |p| p.variants.count }

# ✅ Eager load
products = Spree::Product.includes(:variants).all
```

## Schema Conventions in This Project
- Soft deletes via `deleted_at` (paranoid pattern)
- `private_metadata` / `public_metadata` JSONB for extensible data
- `store_id` for multi-tenancy on major tables
- Prefixed IDs generated by Spree (e.g., `prod_86Rf07xd4z`)
- Mobility translation tables for multi-language fields

## Small Changes (Skip Design Phase)
```bash
# Single nullable field — go straight to implementation
bin/rails generate migration AddNotesToSpreeProducts notes:text
# This creates a simple add_column migration
```
